# Модули 3 и 4: разбор схемы и контрактов

Что это за файл: разбор моей зоны ответственности (Hybrid RAG + Reranker) в трёх
источниках правды — схеме решения, `CONTRACTS-ALL.md` v1.0-draft и коде, который
уже даёт 9.642 на платформе. Цель разбора — найти места, где команда договорится
о разных вещах и потеряет на стыковке.

---

## 1. Где я на схеме

Схема показывает сквозной пайплайн: Frontend → API → Query Processing →
**Retriever → Обзор набора из 6 релевантных фрагментов** → решение о достаточности →
LLM Answer → Верификация → ответ. Модули 3 и 4 объединены в один жёлтый блок и
внутри выглядят как два шага: поиск и «обзор набора из 6 фрагментов».

Слева, отдельной ветвью, — индексация: Извлечение текста и структуры →
Оркестратор чанкинга → эмбеддинги bge-m3 → FAISS Vector Index; параллельно
метаданные → лемматизация → BM25.

Ключевые элементы моей зоны на схеме:

| На схеме | Контракт | Код (`hybrid.py`, `search.py`, `vector_index.py`) |
|---|---|---|
| Retriever (векторы + BM25 + RRF) | `RetrievalRequest → RetrievalResult` | `HybridSearcher.search()` |
| «Обзор набора из 6 релевантных фрагментов» | `RerankRequest → RerankResult`, в примере `top_k: 8` | `_rerank()` + `RERANK_TOP_N = 6` |
| «Решение о достаточности контекста» | отдельного модуля нет, «внутренняя логика модулей 3–5» | `answering.py`: гейт по сырым `best_bm25` и `best_vector` |
| «Повторный поиск (N попыток), переформулировать и расширить» | **в контракте отсутствует** | не реализовано |
| Векторный индекс: **FAISS** | `vector.faiss` в `IndexingResult` | матрица numpy, без FAISS |
| BM25 «с фильтром по метаданным» | `filters` есть, семантика не описана | фильтров нет вообще |

Главное, что видно сразу: **схема и контракт обещают больше, чем есть в коде, и
по-разному**. Ниже — по пунктам, что чинить в контракте, что в схеме, что в коде.

## 2. Три дефекта, которые ломают стыковку (чинить обязательно)

### 2.1. Контракт не передаёт сырые оценки — а на них стоит отказ

Наш гейт отказа (`answering.py`) работает на **сырых** значениях:

```python
REFUSAL_BM25_MIN = 4.0      # лучший сырой BM25 по кандидатам
REFUSAL_VECTOR_MIN = 0.30   # лучшее косинусное сходство
if best_bm25 < REFUSAL_BM25_MIN and best_vector < REFUSAL_VECTOR_MIN:
    → отказ «в базе нет документов»
```

В `RetrievalResult` контракта есть только `rrf_rank` и `rrf_score`. **`rrf_score`
для порога непригоден**: он зависит от `k`, от числа списков и от глубины
(`1/(60+1) = 0.0164` для одного метода, `0.0328` для двух). Один и тот же набор
фрагментов при `k=60` и `k=10` даёт разные числа, а смысл «нашлось ли что-то»
один и тот же.

Итог: если модуль 5 или пайплайн захочет отказать по «слабым сигналам», у него
не будет данных. Значит либо отказ уезжает внутрь модуля 3 (и тогда он не виден
в контракте и не тестируется отдельно), либо отказ вообще не работает.

**Правка v1.1 — добавить в `RetrievedCandidate`:**

```json
"scores": { "bm25": 12.4, "vector": 0.83 }
```

и в `RetrievalResult`:

```json
"stats": {
  "max_bm25": 12.4,
  "max_vector": 0.83,
  "n_above_bm25_gate": 3,
  "n_above_vector_gate": 5,
  "gates": { "bm25_min": 4.0, "vector_min": 0.30 }
}
```

`stats` — это ровно то, на чём принимается решение о достаточности, и его можно
проверить на фикстурах без запуска модели.

### 2.2. `rrf_score` невоспроизводим: не переданы `k` и веса

В контракте `rrf_score: number`, в примере `0.0325` — это классический RRF
с равными весами при `k=60` (два метода поставили фрагмент на 1-е место:
`1/61 + 1/61`).

У нас слияние **неравноправное**, и это измеренное решение:

```python
BM25_WEIGHT = 0.1        # голос BM25 стоит десятую часть голоса векторов
BM25_FUSION_DEPTH = 5    # учитываем только первые 5 мест BM25
RRF_K = 60
```

Причина в коде описана: на нашей базе векторы дают hit@1 ≈ 0.88, BM25 ≈ 0.53.
При равных весах лидер BM25, которого векторы поставили вторым, обгоняет
правильный фрагмент — качество падает относительно одного векторного поиска.

Контракт с примером на равных весах подтолкнёт соседа реализовать классический
RRF, и мы получим два разных ранжирования под одним именем «RRF».

**Правка v1.1 — добавить в `RetrievalRequest`:**

```json
"fusion": {
  "k": 60,
  "weights": { "bm25": 0.1, "vector": 1.0 },
  "bm25_depth": 5
}
```

и возвращать применённые значения в `RetrievalResult` тем же блоком `fusion`.
Формула в контракте: `score = Σ w_m · 1/(k + rank_m)`, где `rank_m` — место
в списке метода `m`, учитываются места не дальше `depth_m`.

### 2.3. Мультизапросность не описана

`search_queries` содержит 1–3 формулировки, но контракт не говорит, **как они
складываются**. Варианты дают разный результат:

* (а) каждый запрос → свой список векторов + свой список BM25 → все списки в один
  RRF с весом `w/m`;
* (б) списки по запросам складываются, затем один RRF;
* (в) поиск только по `standalone_query`, `search_queries` игнорируются.

Сейчас в коде реализовано (в): `hybrid.search()` принимает **один**
`query_text`; мультизапросность живёт в `query_prep.py` и сводится к одной
строке. Это осознанно (быстрее и на нашей базе не проигрывает), но контракт
обещает (а) или (б).

**Правка v1.1:** зафиксировать вариант (а) как целевой, а в v1.0 допустимым
считать (в) при явном `"multi_query": "single"` в запросе. Иначе сосед будет
ждать объединения трёх запросов, а получит поиск по одному.

### Схема (то, что стоит поправить на картинке)

1. **«Решение о достаточности контекста»** нарисовано внутри блока 3–4, а
   контракт говорит «внутренняя логика модулей 3–5». Третья трактовка. Предлагаю
   явно: модуль 3 возвращает `stats` (см. 2.1), решение принимает пайплайн. На
   схеме — вынести ромб **после** модуля 4 и подписать «порог считается по stats».
2. **«Повторный поиск (N попыток), переформулировать и расширить»** — цикл
   изображён, в контракте его нет, и по смыслу он не мой: переформулировка — это
   модуль 2. Стрелка должна идти из ромба достаточности **в модуль 2**, а не
   внутри 3–4. Иначе на защите спросят «где реализован повторный поиск», и
   окажется, что нигде.
3. **FAISS** подписан как факт. У нас матрица numpy: на 360 фрагментах ANN не
   нужен, поиск занимает микросекунды. Либо оставить FAISS как обещание и
   реализовать (`faiss` нет в `requirements_allowed.txt` — проверить!), либо
   переподписать «векторный индекс (numpy/FAISS)». Я бы переподписал: обещать в
   отчёте то, чего нет в коде, — риск на защите.
4. **BM25 «с фильтром по метаданным»** — единственное место на схеме, где
   фильтры вообще упомянуты, а в коде их нет. Либо убрать уточнение, либо
   сделать (см. 3.3).
5. У левой ветви (индексация) нет номера модуля, хотя в контракте это модуль 6.
   На картинке читается как часть модулей 3–4 — при защите разделение
   обязанностей размывается.

## 4. Что контракт требует, а наше решение не производит

Это главный риск: команда начнёт строить API и модуль 5 на полях, которых
`solution.py` не даёт.

| Поле контракта | Есть в нашем чанке (`chunking.Chunk`) | Комментарий |
|---|---|---|
| `chunk_id` | да (`<doc_id>::п. 6.2#0`) | формат другой: контракт ждёт `kb-v1:doc:rev:sec` |
| `document_id` | есть аналог `doc_id` | переименовать в адаптере |
| `text` | да | |
| `section` | да (`label` + `section`) | у нас два поля: номер пункта и заголовок раздела |
| `document_title` | да (в `prefix`, склеено с реквизитами) | нужен разбор, не готовое поле |
| `document_type`, `document_number` | нет | выводятся из текста шапки, но не выделены |
| `revision_id`, `effective_from`, `effective_to` | **нет** | редакция определяется эвристикой по тексту («в редакции 2025 г.»), дат действия в базе нет |
| `page`, `source_path` | **нет** | документы текстовые, страниц нет; путь есть в исходном ZIP, но не сохраняется |

Вывод: контракт v1.0 описывает **целевое** хранилище, а не текущее. Пока это не
разведено, любой код по контракту будет падать на наших данных.

**Правка v1.1:** в таблицу типов добавить колонку «обязательность»:
`required` (chunk_id, document_id, text, section) и `derived_or_null`
(document_title, document_type, document_number, revision_id, effective_*,
page, source_path). Отдельным правилом: если поле не выведено из документа —
`null`, а не догадка; модуль 5 обязан работать при `null` в любом из них.

| Фильтры по `document_id` / `document_number` / `document_type` | ✅ точное совпадение после нормализации (`№ А-08/2024` = `а-08/2024`), `filtered_out` при пустом результате |
| Тип документа в терминах контракта | ✅ `contract / law / regulation / memo / letter / supplement`, неизвестный → `null` |
| `event_date` | ⚠️ не фильтрует: дат действия у документов нет. Правило зафиксировано — отсутствие данных не равно неприменимости |
| Реранк: подмножество, сохранение `rrf_rank`/`matched_by`, `rank`, `dropped` | ✅ |
| Пустой вход → `chunks: []`, нулевые `stats` | ✅ |

### Не закрыто — и это осознанно

| Что | Почему | Кто решает |
|---|---|---|
| **Мультизапросность** (`search_queries`, 1–3 формулировки) | поиск идёт по `standalone_query`; слияние нескольких запросов — архитектурное решение, влияет на время прогона | команда, вопрос №3 |
| **`limits` не применяются** | принимаются и возвращаются эхом, но `vector_top_k`/`bm25_top_k` берутся из `config.py` | можно включить за 20 минут, если нужно |
| **`revision_id`, `effective_from/to`** | в базе нет метаданных редакций: редакция указана в тексте документа | контракт должен разрешить `null` |
| **`page`, `source_path`** | документы текстовые, страниц нет | контракт должен разрешить `null` |
| **`chunk_id` другого вида** | `kb-v1:<doc_id>::п. 6.2#0` вместо `kb-v1:doc:rev:sec` — в нашем id нет редакции, потому что её нет в данных | контракт: разрешить любой стабильный id |
| **HTTP-обвязка модулей** | модули — библиотека; сервером владеет модуль 1 | модуль 1 |
| **Реранк на `/rerank`** | проверен код деградации, но живьём на Qwen3 Reranker не гонялся: локально эндпоинта нет | проверка на платформе |

### Итог одной строкой

Код **соответствует контракту там, где контракт однозначен**, и явно объявляет
`null` там, где данных нет. Полного соответствия быть не может, пока контракт
v1.0 в шести местах допускает разные прочтения (§2–§4) — поэтому следующий шаг
не код, а v1.1: зафиксировать `stats`, `fusion`, `cite_label`, `status`,
`score_kind`, `document_type` и колонку «обязательность» полей.
