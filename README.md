# ПСБ: юридический ИИ-ассистент (RAG)

Ассистент для юристов отвечает на вопросы о договорах, внутренних регламентах компании и статьях
законов строго по базе знаний. Каждый вывод подтверждается ссылкой на документ и пункт.
Ассистент учитывает дату события и редакцию документа, исправляет ошибочные предпосылки
в вопросе и прямо говорит, когда ответа в базе нет.

| Что | Где |
|---|---|
| Веб-чат с источниками | `API/` (FastAPI + HTML), запуск: `docker compose up --build` |
| Сабмит для платформы (LLM-судья) | `platform_solution/solution.py`, архив: `python platform_solution/build_zip.py` |
| Модульный конвейер команды | корневой `solution.py`, модули `query_processing_module/`, `data_processing/`, `rag_pipeline/`, `answer_generation/` |
| База знаний | `data/knowledge-base.zip` (21 документ: 8 документов ООО «Меридиан», 13 статей законов) |

Веб-чат и сабмит используют один движок, поэтому в интерфейсе ассистент отвечает так же,
как при автоматической проверке.

## Быстрый старт: веб-чат

```bash
cp .env.example .env          # укажите LLM_BASE_URL, LLM_API_KEY, LLM_MODEL, RERANKER_MODEL
docker compose up --build     # http://localhost:8000
```

Без Docker (Python 3.10+):

```bash
python -m pip install -r requirements.txt
python -m uvicorn API.app:app --port 8000
```

Возможности интерфейса:

- диалог с учётом истории (ответ на последнюю реплику с контекстом предыдущих);
- под каждым ответом список источников: вид документа (закон или документ компании),
  статус редакции («утратил силу с 01.03.2025»), выдержка;
- «Открыть документ» показывает полный текст с подсветкой использованного фрагмента;
- три тестовых пользователя с раздельной историей (SQLite), кнопка «Новый диалог»;
- строка состояния: модель, готовность векторного индекса, реранкер.

Без ключа LLM чат запускается и показывает найденные положения базы знаний, но не формирует ответ.

API: `POST /api/chat` (`{"question": "...", "history": [{"role": "user", "content": "..."}]}`),
`GET /api/history`, `DELETE /api/history`, `GET /api/documents`, `GET /api/documents/{id}`,
`GET /api/health`.

## Сабмит на платформу

```bash
python platform_solution/tests/test_solution.py   # офлайн-тесты, HTTP подменяется
python platform_solution/build_zip.py             # platform_solution/dist/platform_submission.zip
```

Архив содержит `solution.py` и `requirements.txt` в корне. Скрипт читает `DATA_DIR/questions.csv`
и `DATA_DIR/knowledge-base.zip` и пишет `submission.csv` (`id`, `answer`). Он укладывается
в 20 минут: общий лимит 18 минут, при нехватке времени включается быстрый режим, файл
обновляется по ходу работы. Подробности в [platform_solution/README.md](platform_solution/README.md).

## Как формируется ответ

```
knowledge-base.zip
  └─ разбор документов: вид, статус редакции, номера договоров, контрагенты,
     связи «допсоглашение → договор», «редакция ↔ редакция»; удаление строк-инструкций для ИИ
       └─ фрагменты по пунктам и статьям (~1100 символов)
            └─ гибридный поиск: BM25 со стеммингом + bge-m3 (RRF) → Qwen3 Reranker
                 └─ фильтр по контрагенту и номеру договора из вопроса
                      └─ контекст: документы с шапкой (название, краткая ссылка, статус редакции)
                           └─ DeepSeek: краткий анализ → ответ со ссылками на пункты
                                └─ проверка чисел по источникам → одна правка при расхождении
```

## Контроль достоверности

| Риск | Что делает решение |
|---|---|
| Выдуманные факты и суммы | Каждое число в ответе сверяется с текстом документов и вопроса. Если числа там нет, модель один раз переписывает ответ. |
| Ссылки на несуществующие документы | Модель видит только документы из базы, у каждого есть готовая краткая ссылка («ТК РФ, ст. 70»). Нумерация вида «документ 1» в ответе запрещена. |
| Похожие контрагенты (Альфа-Трейд и Альфа-Трейдинг) | Названия сравниваются по основам слов, договоры других контрагентов исключаются из контекста. |
| Устаревшая редакция | У каждой редакции есть статус («утратил силу с …»), модель выбирает редакцию по дате события. |
| Допсоглашения и письма, меняющие общее правило | Связанные документы попадают в контекст вместе с основным. |
| Ложная предпосылка в вопросе | Правило промпта: исправить ошибку по документу, а не соглашаться с ней. |
| Prompt injection в документе | Строки-инструкции для ИИ вырезаются до поиска и не попадают к модели. |
| Нет ответа в базе | Ответ прямо говорит, каких сведений нет, без догадок и внешних знаний. |
| Сбой API | Повторы с паузой; без эмбеддингов или реранкера поиск идёт на BM25; без LLM пользователь видит найденное положение. |

## Структура

```
API/                      веб-чат: app.py (FastAPI), engine.py (движок), static/index.html
platform_solution/        сабмит для LLM-судьи: solution.py, тесты, сборка ZIP, локальная оценка
query_processing_module/  модуль 2: подготовка запроса (контекст диалога, фильтры, формулировки)

```

## Модульный конвейер

Это альтернативная реализация из отдельных модулей. Каждый модуль обращается к LLM отдельно
(подготовка запроса, генерация, проверка). Для сабмита используется `platform_solution`,
поскольку он делает один-два вызова LLM на вопрос и укладывается в лимит времени.

`solution.py` читает `DATA_DIR/questions.csv` с колонками `id,question` и архив
`DATA_DIR/knowledge-base.zip`. Запуск создаёт `submission.csv` в текущем
каталоге и `ARTIFACTS_DIR/answer_trace.jsonl` с фрагментами и проверкой ответов.
Запросы к поиску и построение индекса выполняют существующие компоненты команды.

```bash
python3 -m venv .venv-local
. .venv-local/bin/activate
python -m pip install -r requirements.txt
cp -n .env.example .env
# Задайте параметры LLM и эмбеддингов в .env.
python solution.py
```

Локальный пример вопросов находится в `data/demo_questions.csv`; для запуска
его можно скопировать в `data/questions.csv`. Платформа предоставляет свой CSV.

```bash
make chunks                 # ZIP -> artifacts/chunks.jsonl, без сети
make index                  # построить или загрузить индекс эмбеддингов
make reindex                # принудительно пересчитать индекс
make verify                 # повторно проверить сохранённые ответы
```

Для другого интерпретатора используйте, например, `make index PYTHON=.venv-local/bin/python`.
`DATA_DIR` и `ARTIFACTS_DIR` действуют и для Makefile, и для `solution.py`.
Векторный индекс сверяется с версией корпуса и названием модели. При запуске
`solution.py` отсутствие доступа к эмбеддингам переводит поиск на BM25; команды
`make index` и `make reindex` сообщают об ошибке, если индекс построить нельзя.

`QUERY_PROCESSING_MODE` выбирает `single` или `multi`, `MAX_WORKERS` управляет
параллельностью. `ANSWER_VERIFY_MAX_RETRIES=2` означает одну первоначальную и
до двух повторных генераций. Если ссылки или смысл не удаётся подтвердить, в CSV
попадает отказ с объяснением недостаточности подтверждения.

Проверка является частью модуля генерации и выполняется до записи CSV. Её можно
вызвать повторно отдельно:

```bash
python -m answer_generation.verify --submission submission.csv \
  --trace artifacts/answer_trace.jsonl --out submission.verified.csv \
  --out-trace artifacts/answer_trace.verified.jsonl
```

Отдельный запуск заново проверяет ссылки и смысл, а при ошибках перегенерирует
ответ по актуальным фрагментам. По умолчанию он пишет исправленные копии и не
перезаписывает исходные файлы. Проверка LLM является оценкой поддержки, а не
гарантией юридической правильности. Связи документов учитываются в том объёме,
в котором их предоставляют поисковые модули команды.

### Проверка качества и отправка

```bash
make benchmark PYTHON=python3.12  # поиск без сети на демонстрационных вопросах
make test PYTHON=python3.12       # проверки, включая запуск распакованного ZIP
make demo PYTHON=python3.12       # LLM-прогон демо в artifacts/demo/
make submit PYTHON=python3.12     # ZIP для загрузки на платформу
```

`make submit` автоматически обходит импорты от `solution.py` и отдельного
проверяющего скрипта. Новый импортируемый модуль попадает в архив без ручного
добавления в список. В ZIP лежат только корневые Python-файлы и зафиксированные
зависимости. Рядом создаётся manifest JSON с хешами исходников и архива.

Демонстрационные ответы `data/demo_output.csv` и разметка
`tests/fixtures/demo_evidence.json` нужны только для разработки.
`solution.py` их не читает, в ZIP они не включаются. Benchmark измеряет покрытие
подтверждающих положений в контексте, а не платформенный балл.

CSV-диалог разбирается на последнюю реплику и историю того же вопроса.
Поисковые формулировки кодируются одним батчем, объединяются по ID и проходят
один общий реранж. В контекст добавляются соседние положения, допсоглашения
и альтернативные редакции с известными датами. Встроенные команды для ИИ
исключаются из контекста. Короткие ID `S1` и `S2` в ответе модели код переводит
в исходные ID корпуса и проверяет до вывода.

150 слов — рекомендация генератору; жёсткий предел — 10 000 символов.
Готовые CSV и JSONL сохраняются после каждого вопроса. INFO-лог содержит
статус, число источников, время и причины отказа для каждого ID.
Полные ответы модели включаются переменной `LLM_LOG_RESPONSES=1`.

Дополнительные параметры: `CONTEXT_MAX_SOURCES=24`, `CONTEXT_MAX_CHARS=24000`,
`INDEX_TIME_BUDGET_SEC=240`, `TIME_BUDGET_SEC=1140` (не более 1170 секунд),
`LLM_MAX_RETRIES=2` для временных ошибок 429/5xx/сети.

Локальный демо-прогон требует действительных настроек LLM; на платформе их
подставляет окружение. Выходные пути можно указать явно:

```bash
python3.12 solution.py --questions data/demo_questions.csv \
  --out artifacts/demo/submission.csv --trace artifacts/demo/answer_trace.jsonl \
  --mode single
```
