# ПравоКонтур — юридический ИИ-ассистент

Веб-ассистент отвечает на вопросы по базе договоров, внутренних документов и нормативных актов. Ответ строится по найденным фрагментам и содержит ссылки на источники. Для пакетной обработки вопросов предусмотрен отдельный запуск через корневой файл solution.py.

**Репозиторий:** [github.com/Zoom7122/PSB_hack-and-change-2026](https://github.com/Zoom7122/PSB_hack-and-change-2026)

## Быстрый запуск

### Требования

- Docker Engine и Docker Compose v2
- Git
- доступ к OpenAI-совместимому API для генерации ответов; для семантического поиска также нужен доступ к модели эмбеддингов

### Установка и настройка

Откройте терминал и выполните команды из каталога, куда хотите скачать проект:

~~~bash
git clone https://github.com/Zoom7122/PSB_hack-and-change-2026.git
cd PSB_hack-and-change-2026
cp .env.example .env
~~~

Откройте файл .env и замените значения настроек модели на свои:

- LLM_BASE_URL — адрес OpenAI-совместимого API;
- LLM_API_KEY — ваш ключ доступа;
- LLM_MODEL — модель генерации;
- EMB_MODEL — модель эмбеддингов; в шаблоне указана baai/bge-m3;
- RERANKER_MODEL — модель переранжирования, если провайдер её поддерживает.

Ключ храните только в локальном .env: этот файл исключён из Git и Docker build context. Не вставляйте реальные ключи в README, исходный код или публичные логи. Для запуска нужен архив базы знаний data/knowledge-base.zip; он уже лежит в репозитории.

### Запуск веб-приложения

Выполните из корня проекта:

~~~bash
docker compose -f compose.yaml -f compose.prod.yaml up -d --build --remove-orphans
~~~

После запуска откройте:

- Веб-интерфейс: [http://localhost:8000](http://localhost:8000)
- Проверка состояния API: [http://localhost:8000/api/health](http://localhost:8000/api/health)

Frontend-контейнер раздаёт страницу и проксирует запросы /api/ в backend. В production-профиле наружу опубликован только frontend. Backend доступен внутри сети Docker Compose.

### Проверить логи и остановить проект

~~~bash
docker compose -f compose.yaml -f compose.prod.yaml ps
docker compose -f compose.yaml -f compose.prod.yaml logs -f backend
docker compose -f compose.yaml -f compose.prod.yaml down
~~~

Обычная команда down сохраняет том assistant-data с историей диалогов и файлами индекса. Для применения новых настроек из .env пересоздайте контейнеры:

~~~bash
docker compose -f compose.yaml -f compose.prod.yaml up -d --build --force-recreate
~~~

При первом запуске backend загружает архив документов. Если настроены эмбеддинги, векторный индекс строится в фоне; до его готовности поиск может использовать BM25.

### Режим разработки

Если нужно обращаться к backend напрямую и смотреть логи контейнеров через Dozzle, используйте дополнительный dev-файл:

~~~bash
docker compose -f compose.yaml -f compose.dev.yaml up -d --build --remove-orphans
~~~

В dev-режиме API доступен по адресу [http://localhost:8001/api/health](http://localhost:8001/api/health), Dozzle — [http://localhost:9999](http://localhost:9999). Dozzle подключён к Docker socket, поэтому оставляйте его доступным только на локальной машине.

Остановка dev-режима:

~~~bash
docker compose -f compose.yaml -f compose.dev.yaml down
~~~

## Архитектура развёртывания

В production используются два контейнера: frontend на Nginx и backend на FastAPI. Docker Compose запускает их в одной внутренней сети. SQLite-файл истории и артефакты сохраняются в именованном томе.

~~~mermaid
flowchart LR
    browser["Браузер"]
    frontend["Frontend<br/>Nginx + веб-страница<br/>proxy для /api/"]
    backend["Backend<br/>FastAPI + LegalAssistant"]
    kb[("data/knowledge-base.zip")]
    volume[("assistant-data<br/>SQLite + артефакты")]
    llm["OpenAI-совместимый API<br/>LLM / embeddings / reranker"]
    dozzle["Dozzle<br/>только dev-режим"]
    socket["Docker socket"]

    browser --> frontend
    frontend -->|"/api/*"| backend
    backend -->|"читает документы"| kb
    backend -->|"история и артефакты"| volume
    backend <-->|"модели"| llm
    dozzle --> socket
~~~

## Как обрабатывается вопрос

Веб-чат и CSV-запуск используют общий основной движок из platform_solution. При проблеме с основным ответом backend может обратиться к резервному модульному конвейеру. Ответ резервного конвейера возвращается только после проверки источников.

~~~mermaid
flowchart TD
    question["Вопрос + история диалога"]
    api["FastAPI<br/>проверка запроса и диалога"]
    core["platform_solution<br/>основной движок"]
    parse["Разбор вопроса<br/>идентификаторы и ограничения"]
    search["Поиск кандидатов<br/>BM25 + векторы, если доступны"]
    fuse["Объединение ранжирований<br/>и reranker"]
    context["Контекст документов<br/>связанные договоры и редакции"]
    llm["Генерация ответа<br/>по найденным документам"]
    verify["Проверка чисел<br/>и ссылок на источники"]
    response["Ответ со ссылками<br/>сохранение в историю"]
    recovery["Резервный путь<br/>модульный поиск"]
    recovery_check["Проверка источников<br/>и ответа"]
    extractive["Короткий ответ по найденному фрагменту<br/>или сообщение о недостатке данных"]

    question --> api --> core --> parse --> search --> fuse --> context --> llm --> verify --> response
    core -. "сбой или неполный ответ" .-> recovery
    recovery --> recovery_check --> response
    recovery_check -. "ответ не подтверждён" .-> extractive
    core -. "LLM недоступна" .-> extractive
~~~

## Модули проекта

| Каталог или файл | Назначение |
| --- | --- |
| API/ | HTTP API, управление диалогами, соединение веб-интерфейса с движком, CSV-адаптер и резервный путь |
| API/static/ | Страница веб-чата |
| platform_solution/ | Основной автономный движок: загрузка документов, BM25 и векторный поиск, контекст, генерация и проверки |
| data_processing/ | Извлечение и нормализация текста, разбиение на фрагменты, BM25, векторный индекс и гибридное ранжирование |
| rag_pipeline/ | Корпус и метаданные, поиск и фильтры, связанные документы, индексы и сохранение результатов |
| query_processing_module/ | Подготовка вопроса и структуры поискового запроса; одиночный и многоэтапный режимы |
| answer_generation/ | Форматирование утверждений, проверка ссылок и содержания ответа, повторная генерация после ошибок |
| deploy/ | Nginx-конфигурация и Dockerfile frontend |
| compose.yaml, compose.prod.yaml, compose.dev.yaml | Общая, production- и dev-конфигурации Docker Compose |
| data/knowledge-base.zip | Пример базы знаний |
| solution.py | Точка входа пакетного CSV-запуска |

Python-пакеты разделены по ответственности, но сейчас не запускаются отдельными контейнерами. В production это один backend-сервис и отдельный frontend-сервис. Резервный модульный конвейер включается из backend при сбое основного пути; он не требует отдельного сетевого сервиса.

## Принятые технические решения

| Решение | Почему оно подходит проекту |
| --- | --- |
| Один основной движок для веб-чата и пакетного запуска | Логика поиска и ответа не расходится между демонстрацией и обработкой CSV |
| BM25 вместе с векторным поиском | BM25 хорошо находит точные номера, даты и формулировки; эмбеддинги помогают искать смысловые совпадения |
| Объединение ранжирований и reranker | Сначала собирается широкий список кандидатов, затем модель уточняет порядок наиболее подходящих фрагментов |
| Связанные документы добавляются в контекст | Ответ о договоре может зависеть от дополнения или редакции документа |
| Проверка чисел и цитат перед выдачей | Снижает риск выдать неподтверждённый номер или ссылку; при ошибке основной путь может перейти к резервной обработке |
| Nginx отдельно от FastAPI | Frontend обслуживает статические файлы, а backend не нужно публиковать в production напрямую |
| SQLite и именованный Docker-том | История остаётся после пересборки контейнеров и не требует отдельного сервера базы данных для демонстрации |
| OpenAI-совместимый API через переменные окружения | Адрес сервиса и модели можно менять без правки исходного кода |

### Масштабирование и границы текущего развёртывания

Границы Python-модулей позволяют менять поиск, подготовку запроса или проверку ответа независимо на уровне кода. Сейчас же модули собраны в одном backend-образе, чтобы запускать решение одной командой и не добавлять сетевые вызовы между внутренними шагами.

Текущая конфигурация рассчитана на один backend-контейнер: история хранится в локальном SQLite-файле в Docker-томе, а часть поискового состояния работает внутри процесса. Для нескольких реплик backend сначала потребуется вынести историю в общую базу данных и согласовать хранение поисковых индексов. Отдельный frontend уже может обращаться к backend через внутреннюю сеть Compose.

Веб-интерфейс содержит три демонстрационных профиля без полноценной аутентификации. Не используйте его в качестве публичного многопользовательского сервиса без добавления авторизации и разграничения доступа.

## Пакетная обработка вопросов

Корневой solution.py читает CSV с колонками id и question, обрабатывает вопросы и сохраняет результаты в submission.csv. Вопросы можно запускать локально на примере из репозитория.

Установите зависимости из корня проекта:

~~~bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt -r platform_solution/requirements.txt
~~~

Запустите пример:

~~~bash
python solution.py \
  --questions data/demo_questions.csv \
  --out artifacts/demo/submission.csv \
  --trace artifacts/demo/answer_trace.jsonl
~~~

Входная база должна содержать knowledge-base.zip; для стандартного запуска используется каталог data. Настройки LLM берутся из окружения или локального .env. Параметры параллельности и бюджета времени задаются через SOLUTION_WORKERS и SOLUTION_TIME_BUDGET.

## Важно

Ассистент формирует ответы по загруженному корпусу и проверяет привязку выводов к найденным источникам. Это помогает быстро находить нужные документы, но не заменяет проверку специалистом. Качество ответа зависит от полноты и актуальности базы знаний, а также доступности настроенных моделей.
