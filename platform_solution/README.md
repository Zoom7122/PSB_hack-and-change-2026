# Решение для автоматической проверки (LLM-судья)

Самодостаточный `solution.py` для платформы ПСБ. Платформа переносит только корневые
`.py` и `requirements.txt`, поэтому решение собрано в один файл. Нужна только `httpx`;
`numpy` ускоряет векторный поиск, но не обязательна.

## Что делает

1. **База знаний.** Читает TXT, MD и DOCX из `knowledge-base.zip`. Для каждого документа определяет:
   - вид: закон или внутренний документ;
   - статус редакции: «УТРАТИЛ СИЛУ с …», «действует с …»;
   - номера договоров;
   - контрагентов (ООО «…»);
   - связи: допсоглашение ↔ договор, редакция ↔ редакция.

   Строки-инструкции для ИИ (prompt injection, как в записке ЮО-7) вырезаются до поиска.
2. **Фрагменты.** Документы режутся по пунктам и статьям, около 1100 символов на фрагмент.
3. **Поиск.** BM25 со стеммингом и bge-m3 объединяются через RRF, затем результат уточняет реранкер (`RERANKER_MODEL`).
   - Если не работают эмбеддинги или реранкер, остаётся BM25.
   - Если в вопросе назван контрагент или номер договора, берутся его документы, а договоры других контрагентов исключаются: «Альфа-Трейд» ≠ «Альфа-Трейдинг».
   - Падежи учитываются: «Северным Складом» найдёт «Северный Склад».
   - В диалогах приоритет у последней реплики пользователя.
4. **Контекст.** До четырёх документов плюс связанные с ними. Короткие документы передаются целиком, у длинных законов — только релевантные выдержки. У каждого документа есть шапка со статусом и краткой ссылкой («ТК РФ, ст. 70»).
5. **Генерация.** Один вызов LLM. Модель кратко пишет `АНАЛИЗ` (документ, дата, редакция, ложная предпосылка), затем `ОТВЕТ`. Правила в промпте покрывают:
   - ответ только по документам и честный отказ, если данных нет;
   - прямой ответ в первой фразе и ссылку на пункт;
   - ловушки базы: похожие контрагенты, редакции по дате, допсоглашения, неверные цифры в вопросе, инъекции.
6. **Проверка.** Каждое число, номер пункта («п. 3.1»), статьи («ст. 70») и документа («П-17/2024») в ответе должны быть в документах или в вопросе. Если это не так, делается одна правка с указанием выдуманных значений; правка принимается, только если замечаний стало меньше. Если модель написала анализ, но не дошла до ответа, итоговая часть запрашивается отдельно.
7. **Надёжность.**
   - `submission.csv` создаётся сразу и перезаписывается по ходу работы.
   - Общий лимит — 18 минут; ни один сетевой запрос его не превышает.
   - Когда времени мало, решение переходит в быстрый режим без реранкера и анализа.
   - Если LLM недоступна, в ответ попадает извлечённое положение документа.

## Команды

```bash
python tests/test_solution.py     # офлайн-тесты, HTTP подменяется
python build_zip.py               # dist/platform_submission.zip для загрузки
DATA_DIR=../data python solution.py   # локальный запуск (нужны LLM_BASE_URL/LLM_API_KEY/LLM_MODEL)
python evaluate.py                # оценка submission.csv по эталону demo_output (LLM-судья)
```

`data/questions.csv` для локального запуска — копия демо-вопросов. В `answer_trace.jsonl`
для каждого вопроса записываются режим, использованные документы, найденные расхождения
и время.

## Переменные окружения

Решение читает переменные платформы: `LLM_BASE_URL`/`OPENAI_BASE_URL`, `LLM_API_KEY`/`OPENAI_API_KEY`,
`LLM_MODEL`/`GEN_MODEL`/`OPENAI_MODEL`, `EMB_MODEL`, `RERANKER_MODEL`, `TEMPERATURE`, `MAX_TOKENS`
(минимум 1400), `MAX_WORKERS` (2–8), `DATA_DIR`.

Дополнительные переменные:

| Переменная | Назначение |
|---|---|
| `SOLUTION_TIME_BUDGET` | Общий лимит времени в секундах, по умолчанию 1080 |
| `SOLUTION_WORKERS` | Число параллельных вопросов; переопределяет `MAX_WORKERS` |
| `USE_EMBEDDINGS=0` | Отключить эмбеддинги |
| `USE_RERANKER=0` | Отключить реранкер |
| `ANSWER_TRACE=0` | Не писать журнал `answer_trace.jsonl` |
